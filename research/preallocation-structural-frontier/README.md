# Phase 11 — pre-allocation structural frontier

Status: **development shadow investigation**  
Baseline: `43745d086c4879af69181676149ebcfb76110502` (Phase 10 squash)  
Research branch: `r-and-d/phase-11-preallocation-structural-frontier`

## Question

Can a deterministic structural frontier immediately before `assignClueTextCellsV2` retain the candidates that feed the accepted Phase 10 complete-pipeline frontier while avoiding most exact clue-allocation calls?

## Non-negotiable boundary

Exact clue allocation, complete validation and the accepted Phase 10 final comparison remain authoritative. Every experiment in this ledger is browser-default-off and shadow-only. No result below changes production output or ownership.

```text
SCANWORD_PREALLOCATION_STRUCTURAL_FRONTIER=off|shadow
SCANWORD_PREALLOCATION_STRUCTURAL_FRONTIER_WIDTH=<positive integer>
SCANWORD_PREALLOCATION_DIAGNOSTIC_WIDTHS=<comma-separated widths>
```

The implementable dependency model is staged:

```text
structural base states
-> bounded base retention
-> victim variants from retained parents
-> bounded final structural retention
-> exact clue allocation for retained states
-> accepted Phase 10 complete-pipeline frontier
```

Observed victim coverage in shadow mode is limited to variants generated by Phase 10. Any authoritative implementation would have to generate variants from retained parents before final retention.

## Shared observation boundary

`construction-preallocation-frontier-v1.js` wraps only `ScanwordSolver.generatePortfolio` and observes every state immediately before `assignClueTextCellsV2`. It records:

- build-attempt, baseline-fallback and victim-replacement provenance;
- exact allocation calls and elapsed time;
- geometry, residual topology and repair-potential metrics;
- regional clue-feasibility bounds and pressure;
- Phase 10 construction-frontier ancestry;
- portfolio-wide aggregates across the canonical 2,500- and 3,500-entry working sets.

The heavy observation objects are non-enumerable. Normal payloads contain compact telemetry only.

## Hypothesis C — repair-potential rank only

`construction-preallocation-ranked-frontier-v1.js` is the final narrow test at this boundary. It uses the same deterministic repair-potential ordering but removes pre-allocation dominance entirely:

```text
rank structural bases
-> retain top N bases
-> observe victim variants from retained parents
-> rank bases plus eligible victims
-> retain top N finalists
```

Only the explicit top-N budget can exclude a state. The diagnostic width sweep is:

```text
8,16,24,32,48,64,96,128,160,192,224,256,288,320
```

The rank-only checkpoint separates diagnostic validity from promotion validity. It passes when output parity, telemetry and runtime are valid, then records the smallest width—if any—with full Phase 10 parent and finalist recall across all development seeds.

Run:

```bash
node tools/preallocation-structural-frontier-test-v1.cjs
node tools/preallocation-repair-potential-test-v1.cjs
node tools/preallocation-ranked-frontier-test-v1.cjs

SCANWORD_PREALLOCATION_CONCURRENCY=4 \
SCANWORD_PREALLOCATION_RUNTIME_RATIO=1.12 \
SCANWORD_PREALLOCATION_STRUCTURAL_FRONTIER_WIDTH=16 \
SCANWORD_PREALLOCATION_DIAGNOSTIC_WIDTHS=8,16,24,32,48,64,96,128,160,192,224,256,288,320 \
```

## Decision rule

If rank-only retention reaches full Phase 10 recall at a bounded width with meaningful projected allocation savings, freeze the smallest safe development width and implement a separately gated authoritative filter with an explicit Phase 10 rollback.

If full recall requires retaining nearly every allocation input—or does not occur within the observed maximum—reject pre-allocation retention at this representation. Preserve Phase 10 unchanged and move to the next architectural investigation rather than weakening the complete validator or hiding losses behind average metrics.
